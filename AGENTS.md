# TTRPG Cards

A browser app for laying out and printing tabletop reference cards. It ships a bundled, openly-licensed catalog, lets a user bring their own content, and produces print-ready sheets at real physical dimensions.

The app is **fully static**. `next build` emits an `out/` directory of HTML, CSS, and JS; there is no server, no API, and no backend. Everything (parsing, layout, storage, print generation) happens in the browser.

Monorepo built with pnpm workspaces + Turborepo, Next.js (App Router) and TypeScript, plain CSS via CSS Modules, and Radix primitives wrapped in `@ttrpg-cards/ui`. Domain logic lives in workspace packages (`@ttrpg-cards/*`) and feature slices (`features/*`); `apps/web` is a thin, enforced wrapper.

## Stack

- **Framework**: Next.js App Router, **static export** (`output: "export"`)
- **Language**: TypeScript
- **UI primitives**: **Radix** (`radix-ui`) wrapped in `@ttrpg-cards/ui`
- **Styling**: Plain CSS Modules with native CSS nesting (no Tailwind, no Sass, no styled-components)
- **Runtime validation**: **TypeBox** (`typebox`, v1) re-exported via `@ttrpg-cards/validator`
- **Persistence**: **IndexedDB** for card data, local preferences for small UI state, both behind `@ttrpg-cards/storage`
- **Package manager**: pnpm + Turborepo
- **Node**: see `.nvmrc` for the required version
- **Testing**: Vitest
- **Component workshop**: Storybook, hosted in `@ttrpg-cards/ui`

All third-party packages are pinned to the **latest stable** at add-time. Versions live in the `catalog` in `pnpm-workspace.yaml` and are referenced from manifests as `catalog:`, so a version is declared in exactly one place.

## Monorepo Layout

```
ttrpg-cards/
  apps/
    web/          # Next.js App Router app (thin wrapper: static export config, routes, layouts)
  features/       # feature slices: UI + logic, testable without the framework
    catalog/      # @ttrpg-cards/feature-catalog: the bundled catalog on a page, with live controls
  packages/       # @ttrpg-cards/* workspace packages (each with an explicit `exports` surface)
    card/ core/ srd/ importer/ printer/ storage/ text/ ui/ validator/
```

| Package                  | Owns                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| `@ttrpg-cards/card`      | card domain model, schemas, layout and theme configuration           |
| `@ttrpg-cards/core`      | generic building blocks that do not belong to another package        |
| `@ttrpg-cards/srd`       | bundled openly-licensed catalog, extraction, provenance, attribution |
| `@ttrpg-cards/importer`  | JSON and Markdown parsing into the card model                        |
| `@ttrpg-cards/printer`   | sheet layout, pagination, PDF generation                             |
| `@ttrpg-cards/storage`   | IndexedDB persistence, local preferences                             |
| `@ttrpg-cards/text`      | rich text runs, the marks they carry, and their canonical form       |
| `@ttrpg-cards/ui`        | Radix-based primitives, card renderer, the document theme            |
| `@ttrpg-cards/validator` | TypeBox re-export, the single validation surface                     |

**Dependency direction points inward:** `apps/web` → `features/*` → `packages/*`. `packages/*` never import `features/*` or app code; `features/*` never import `apps/web`. This keeps the app shell swappable and the logic testable in isolation.

A feature slice is a workspace package named `@ttrpg-cards/feature-<slice>` living in `features/<slice>/`. A capability becomes a `packages/*` entry instead when it wraps a third-party dependency we want swappable, or when it is reused across features and must not drift.

**Packages hold domain logic, not only third-party wrappers.** The card model and its schemas are `@ttrpg-cards/card` because `srd`, `importer`, `printer`, `storage` and `ui` all depend on them, and `packages/*` may never import `features/*`. Putting the model in a feature would invert the dependency direction for five packages at once. A feature slice is a slice of the app's UI and behaviour; it is not the home for the vocabulary every slice speaks.

## Content Rules (non-negotiable)

These are the constraints the project exists under. They are not style preferences and they are not negotiable in a review.

- **Nothing the app ships ever transmits.** No server call, no remote fetch of content, no share link, no analytics, no telemetry, no error reporting. The app is static and stays that way. A feature that needs the network does not ship. Lint-enforced, not merely documented: `no-restricted-globals`, `no-restricted-properties`, and `no-restricted-syntax` together ban `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, and `serviceWorker` (including behind a `window.`, `globalThis.`, or `navigator.` prefix), and no package is exempt, `@ttrpg-cards/storage` included. The ban extends to tooling: Storybook, Next, and Turborepo telemetry are all switched off, in the package scripts and again in CI. A name-based rule cannot catch an alias or a computed property, so treat it as a guardrail rather than a proof; the proof is that nothing in `out/` opens a connection.
- **The hosting layer is outside this rule; the user's browser is not.** Analytics a host derives from its own request logs add no code to the bundle and ask nothing of the visitor's machine: that is a deployment decision and this rule does not reach it. A client-side beacon is a different thing entirely: it makes the _user's browser_ transmit, which is precisely what the rule forbids, and it stays off no matter who injects it or how convenient the toggle is. Hosts routinely sell both under one product name, so check which one is switched on rather than trusting the label.
- **One CI job fetches, and it is the only thing in the repository that does.** `Catalog drift` downloads the licensed documents to check the committed catalog still matches its generator. That is a workflow step running on our own infrastructure, not code we ship and not code in the source tree, so the lint rules above still hold everywhere without an exemption. It is also deliberately outside the quality gate: a clone typechecks, tests and builds with no network. Nothing else in CI may reach the network for content.
- **Local persistence is expected and correct.** The user's full card set is stored in their own browser so it survives a reload. Transmission is the line, not persistence.
- **Never fetch content from a third-party source**, not even client-side, not even behind a button the user clicks. The importer reads what it is handed and nothing else.
- **Import parsers stay forgiving.** A parser must accept a range of reasonable input shapes rather than tracking one tool's exact output. This is a hard requirement, not polish.
- **Forgiveness is proved by a matrix, not asserted.** A parser carries one fixture per input shape it promises to accept, all of them the same content spelled differently, and one test that reads every one of them to the same result. A change that quietly narrows it to a single editor's output then fails there rather than in a reader's browser. Round-tripping the bundled catalog through the format is the other half: a few hundred entries of real prose is a harder test than any fixture written to suit the parser.
- **The heading level a card is written at is found, never assumed.** Depth says nothing on its own: one document gives each card an `h1` and the next nests them under a title, and a document that captions a table writes that caption as a heading too. The level that carries the cards is the shallowest one where **more than one** heading has content under it, because cards come in runs and a heading that groups them is one of a kind. Content alone is not enough to tell them apart, since a title with a line of prose under it carries content like any card does.
- **A parser reports what it could not read, with a line number, and never drops it.** A reader who pasted forty cards and got thirty-nine has no other way to find the one that went missing, and silently losing it is worse than refusing the lot.
- **The attribution follows the material, on and off.** The notice is shown wherever the bundled content is, and comes off a page that is showing none of it. That is the ceiling as much as the floor: a credit standing under content the reader wrote reads as the licensor having had a hand in it.
- **No game-system names in tracked files**, not in identifiers, strings, comments, tests, fixtures, file names, docs, or user-facing copy. The one carve-out is the licence attribution statements, which must be reproduced **verbatim** and are therefore exempt.
- **Fixtures are bundled licensed content or original material.** Never a third-party product's file.
- **No trade dress.** Do not imitate any published product's visual identity.

## Project Conventions

### Styling

- Use CSS Modules (`.module.css` files) with native CSS nesting. **The one exception is a stylesheet whose selector is not a class**, such as the card palettes matched on `data-card-theme`: a consumer may set that attribute on any surface above a card, so the selector cannot be scoped to the module that reads it. Such a file lives in the component's directory, is imported by the component, and declares nothing but custom properties. Reach for it only when a class genuinely cannot carry the selector; a global stylesheet is otherwise the thing CSS Modules exist to avoid.
- No CSS utility libraries (Tailwind, etc.). No preprocessors (no Sass/SCSS); plain CSS covers all our needs (nesting, variables, media queries).
- **The document theme lives in `packages/ui/src/theme.css`** and declares the colour, spacing, typography, shape, and elevation properties more than one part of the app shares. `apps/web/app/globals.css` imports it and adds only document-level resets.
- **Never hardcode colours, spacing, or typography.** All values must use custom properties. Add new ones when needed.
- **Declare a custom property at the narrowest scope that covers everything reading it.** A property only one component reads belongs in that component's directory, not in the document theme: `theme.css` is for what the app shares, and a value sitting there that one stylesheet reads is a global whose blast radius is a lie. It also costs every page the bytes. The card's colour themes and type scale are the worked example, in `CardFace/CardFace.themes.css` and `CardFace/CardFace.module.css`, and they are bundled with the card renderer rather than with the document.
- **A card colour theme is a block of custom properties in `packages/ui/src/CardFace/CardFace.themes.css` plus an entry in `CARD_THEMES`, and never anything else.** The card face names its theme through `data-card-theme` and reads the roles; adding one is those two edits, and the stories and the contrast checks pick it up from the registry. A component that branches on a theme's name, or a stylesheet elsewhere that names a card colour, has moved the palette back into the code.
- **`@ttrpg-cards/card` names the themes; `@ttrpg-cards/ui` draws them.** The registry is identity and selection only (`CARD_THEMES`, `CardThemeId`, `isCardThemeId`), which is why it sits beside `CARD_LAYOUT_PRESETS`: both are card configuration a user picks and `@ttrpg-cards/storage` persists, and storage must not depend on a React package to validate what it read back. No CSS and no colour value ever enters `@ttrpg-cards/card`.
- **The ambient module declaration for `*.module.css` lives once, in `types/css-modules.d.ts`.** Any package that imports a stylesheet adds that path to its tsconfig `include` (`"../../types/css-modules.d.ts"`). Never re-declare it per package: six copies of the same declaration is exactly the duplication that drifts. `apps/web` is the exception: `next-env.d.ts` already supplies it.

### Component Structure

Feature/component-based structure. Each component lives in its own directory with only the files it needs:

```
ComponentName/
  ComponentName.component.tsx   # React component, render-only
  ComponentName.module.css      # Scoped CSS module styles
  ComponentName.types.ts        # TypeScript types and interfaces (props, data shapes)
  ComponentName.constants.ts    # Constants and static data
  ComponentName.hooks.ts        # Custom hooks and side-effects (useEffect, etc.)
  ComponentName.data.ts         # Computation and data-shaping logic
  ComponentName.schemas.ts      # TypeBox schemas guarding this component's boundaries
  ComponentName.stories.tsx     # Storybook story (primitives in @ttrpg-cards/ui)
  ComponentName.fixtures.ts     # Sample values shared by the tests and the stories
  ComponentName.test.tsx        # Unit tests, beside the code they cover
  index.ts                      # Public export barrel
```

Not every file is required. Only create what the component needs.

### File Placement Rules

- **Types and interfaces** (e.g. props like `CardFaceProps`) go in the component's `.types.ts` file. Never define types inline in `.component.tsx`.
- **Next.js route files are the exception**: `layout.tsx`, `page.tsx`, and friends keep their props inline, because the framework owns that signature and the file is an adapter rather than a component.
- **`useEffect` hooks** and other side-effects (click-outside handlers, resize observers) go in `.hooks.ts`, never inline in `.component.tsx`.
- **Standalone functions** (encoding helpers, validators, formatters) go in `.hooks.ts` (behaviour helpers) or `.data.ts` (computation). Keep `.component.tsx` focused on rendering.
- **Large computation** (text measurement, overflow splitting, sheet pagination) goes in the owning package, not in a component file.
- **Keep one domain class per implementation file.** Name the file for the class and expose related construction, codec, and query-building behaviour as class statics rather than adjacent `build*` / `encode*` / `decode*` free functions.
- **The helpers a class uses are `#` private statics on it, not module-level free functions.** Module scope in a class file keeps imports, constants and schemas; the behaviour belongs to the class. A free function beside a class reads as a second thing the module offers, it is reachable by anything else added to the file later, and the next person to need it exports it rather than asking where it belongs. Keeping it on the class says who owns it, and the `#` says nobody else may call it.
- **A module with no class keeps plain exported functions.** The rule above is about where a class's behaviour lives, not a preference for classes. Never introduce a class to hold functions that have no instance and no state: that is a namespace wearing a type's clothes, and it makes every caller write a prefix that tells them nothing.
- **SVG icons** are extracted into their own component files in `@ttrpg-cards/ui` and consumed from there. Never embed raw SVG markup in a feature component's JSX, and never reintroduce app-local icon components in `apps/web`.
- **`.test.ts` is reserved for tests**, never for data/computation modules.
- **Every workspace package carries a `README.md`** covering what it owns, the rules specific to it, and the boundaries it keeps. The `src/index.ts` barrel keeps a one-line TSDoc pointing there, enough to show on hover, with the prose somewhere a reader browsing the repo will actually find it. Prose that explains a whole package does not belong in a barrel file.

### Inner Components

- Use inner components for repeated or distinct UI fragments within a feature directory. Inner components drop the parent's prefix (file `TitleRow.component.tsx`, export `TitleRow`) since the surrounding directory conveys scope; only re-add the parent prefix when an inner name would otherwise be too generic to read at a glance.
- **An inner component gets its own directory inside its parent's** (`CardFace/BodyBlock/BodyBlock.component.tsx`), never a separate top-level one and never files sitting flat beside the parent's. It keeps the same file layout as any other component, its own `.module.css` included, so the rules that style it travel with it.
- **An inner directory gets no `index.ts`.** A package's `exports` map maps `"./*"` to `"./src/*/index.ts"`, and `*` matches slashes, so a barrel there would make `@ttrpg-cards/ui/CardFace/BodyBlock` a resolvable public import. The parent's barrel stays the only public surface.
- **An inner component reaches a primitive by its named subpath**, `import { RichTextView } from "@ttrpg-cards/ui/RichTextView"`, not by a relative path. From an inner directory the relative route would be `../../`, which is banned, and the subpath is what the import convention below asks for anyway. Self-referencing a package by its own name resolves through the same `exports` map and needs no self-dependency.

### Imports

- **No parent-relative imports two or more levels up.** Never import from `../../` (or deeper).
- Use `@/...` for cross-directory imports **inside `apps/web`** (the alias resolves to `apps/web/`). Reach feature slices and packages by their workspace names (`@ttrpg-cards/feature-<slice>` and `@ttrpg-cards/<package>`), never through a relative path or a `src/` path.
- Import package primitives from their named subpath: `import { Card } from "@ttrpg-cards/ui/Card"`. Each package's `exports` map keeps the surface explicit and tree-shakeable.
- Sibling imports (`./foo`) and one-level parent-relative imports (`../foo`) are both fine. The latter is how an inner component reaches something in its parent's directory.
- The `no-restricted-imports` ESLint rule enforces these boundaries, including the direction of dependencies and the ownership rules below.

### Runtime Validation

- **Use TypeBox for all runtime JSON-boundary validation.** All schemas import from **`@ttrpg-cards/validator`**, which re-exports TypeBox (`typebox` v1, **not** the legacy `@sinclair/typebox` v0) so we have a single, swappable validation surface. Never import `typebox` directly outside `@ttrpg-cards/validator`.
- Define declarative schemas and validate with `Value.Check` / `Value.Errors`; do not build parallel field-by-field validator trees by hand.
- **Validate every untrusted boundary**: imported files, pasted text, stored records read back from the browser, and URL/query state. Then keep any cross-field/domain assertions a structural schema cannot express as small named helpers.
- **Text the reader sees is rich text; identifiers, keys and attribution are plain strings.** A field rendered on a card is `TextRuns` from `@ttrpg-cards/text`, so any of it can carry emphasis and every consumer handles one shape rather than asking which kind of text it was handed. Ids and search keys never render, and an attribution has to be reproduced exactly as the licensor wrote it, so neither belongs in a structure built to merge and normalise runs.
- **Markup is never stored in a string.** Emphasis is structured, and markdown is an import format: the importer parses it into runs on the way in. A string holding syntax makes every reader of the model a parser, and the one that forgets is quietly wrong. This is a rule about the model, not about import formats: a generated file that an extraction writes may hold markup, so long as exactly one module parses it into runs at the package boundary and nothing downstream sees a marker.
- **That one module is `runsFromMarkup` in `@ttrpg-cards/importer`, and a second one is never written.** Reading markup into runs is the same job whoever wrote the markup, so the bundled extraction and a document a reader pasted go through the same parser and read the same text the same way. A package that holds markup depends on the importer for it rather than keeping a copy: two parsers are two things to keep in step and one of them drifts. The parser is deliberately forgiving and leaves a stray marker as literal characters, so a pipeline that must not ship one validates its own output before writing it.
- **A wire-format key follows the ecosystem's spelling, not our prose's.** Our documentation writes "licence"; the JSON key is `license`, because that is what manifests, licence identifiers and other tools write. Schemas reject unknown fields, which turns a spelling difference into a rejected file rather than an ignored key.
- **Keep reusable wire-format patterns in shared `*.schemas.ts` files** (or a package-level validation module) and compose them into object schemas. Never embed validation regexes in execution or rendering code.

### Dependency Encapsulation & Package Boundaries

- **Every third-party dependency is owned by exactly one package** and reached through that package's stable interface, never imported directly by features or the app. Validation goes through `@ttrpg-cards/validator` (TypeBox), primitives through `@ttrpg-cards/ui` (Radix), persistence through `@ttrpg-cards/storage` (IndexedDB).
- Switching an implementation later means satisfying the same interface; feature and app code never changes. **Enforced by `no-restricted-imports`**, which bans the owned dependency everywhere except its owning package.
- **Only `apps/web` may import the framework.** `next` and `next/*` are banned in `features/*` and `packages/*` so every slice stays unit-testable without Next.js.

### `apps/web` Is a Thin Wrapper (enforced, not asserted)

- `apps/web` owns **only** what is intrinsically Next.js: the route tree (`app/`), root layouts, `next.config.ts`, and the document-level stylesheet.
- Every `page.tsx` is a thin adapter: resolve params → validate (TypeBox) → render a `features/*` component. Route files stay well under ~50 lines.
- **No domain logic and no third-party dependency calls live in `apps/web`.** Quick test: if a piece of code could be unit-tested _without_ Next.js, it belongs in a feature or package, not the app.
- **The app may import only `@ttrpg-cards/ui` and `@ttrpg-cards/validator`**, which is what a thin adapter and the root layout actually need. `no-restricted-imports` bans the domain packages (`core`, `importer`, `printer`, `srd`, `storage`) inside `apps/web`; reach them through a `features/*` slice. They stay in `apps/web/package.json` regardless, because `transpilePackages` needs them resolvable.
- There are **no environment variables and no secrets**. The build produces static files; anything configurable is either a build-time constant in a package or a user preference in `@ttrpg-cards/storage`.
- **A new feature slice is added to `apps/web/package.json` and to `transpilePackages` together.** The app resolves it like any workspace dependency, and Next has to be told to compile the TypeScript it ships.

### Feature Slices

- **A slice is a workspace package** named `@ttrpg-cards/feature-<slice>` in `features/<slice>/`, laid out like a `packages/*` entry: `src/`, an `exports` map, a `README.md`, and the same three scripts. It is not a loose folder of components.
- **A slice exports the component the route renders, and nothing else.** Everything the slice is built from is an inner component of that one, with no `index.ts` of its own, so `exports` cannot turn an internal piece into a public import.
- **A slice that renders runs its tests in `jsdom`**, configured in its own `vitest.config.ts` the way `@ttrpg-cards/ui` does. The rest of the workspace stays in Vitest's default Node environment.
- **A slice is where the app-level rendering test lives.** `apps/web` is a thin adapter with nothing of its own to assert, and a slice tests without the framework, so the test that proves the screen renders belongs here rather than in the app or in a package's stories.

### Card Geometry and Units

- **Dimensions are a live property, not a constant.** Card width and height initialise from the default declared in `@ttrpg-cards/card` and can be changed at runtime; the renderer, the text-fitting routine, and the print pipeline all read from that property.
- **Nothing outside that default declaration may hardcode a card dimension.** If you find yourself typing a card measurement into a component or a stylesheet, read it from the layout configuration instead.
- **Physical units throughout**: millimetres, never pixels, so screen and print agree. That includes font sizes: the fitting range is millimetres like every other length, and the renderer converts once at the boundary where it has to.
- **The layout configuration is `CardLayout`, and it is an immutable value object.** Consumers are handed a layout and read their measurements off it; a different size is a new layout derived with `with`, never a mutation and never a module-level singleton. Several consumers lay out against the same layout at once, so mutating one would change the geometry under the others with nothing to tell them, and a renderer needs the new identity to re-run anyway.
- **A layout is a card size and a text size, picked separately.** `CARD_LAYOUT_PRESETS` holds the box: the dimensions and the margins. `CARD_TEXT_SIZE_PRESETS` holds the band type may be set within. `CardLayout.fromPreset({ preset, textSize, overrides })` combines one of each. Two records because they answer two questions, and neither answer tells you the other: how large a card is cut is a property of the card, how large its type is set is a property of the reader. A preset holding both would make every combination a new entry. Adding either is an entry in its record and the name a picker calls it by, and nothing else. The name is kept beside the record rather than inside the preset, because the layout schema rejects a field it does not know and a label in a preset would make it fail its own validation; `CARD_SIZES` and `CARD_TEXT_SIZES` are each the two together, ordered, and `satisfies` is what stops them drifting apart.
- **The smallest type is what the reader picked, on every part of the card.** Legibility is a property of the reader, not of the card, so the floor never scales with the box: a larger card buys a larger maximum and more room before a split, never a smaller floor. The floor governs every region and not just the body, because each region is a ratio of the body size and a ratio cannot hold a floor. The default is `small`, which floors at 2.38mm, or 9 CSS pixels: the smallest this app is willing to set text at, and the setting that splits the fewest entries.
- **A fixture written to overrun a card pins its own type band.** These tests are about where a split falls, and the shipping text size is a reader's setting that moves for product reasons. A fixture that reads the default turns such a change into a broken split somewhere unrelated, so a test that counts cards states the band it counted at.
- **Name a preset for the size, never for a game or product cut to it.** The default is `standard`, the size most trading and playing cards are made at. Naming it after one of them would be both a game name in the repo and wrong, since the size belongs to none of them.
- **The default's measurements appear in exactly three places**: the preset that declares them, the test that pins them, and the print harness that checks a browser really drew a card that size. A test asserting the default against the constant it came from proves nothing, so those two name the numbers. The same three places a paper measurement gets, and for the same reasons.
- **The domain model carries content, never layout.** No field names a position on the card, and no schema caps a length because a region looks small. Ordered lists let the theme decide how to set them out, and what actually fits is the fitting routine's call against live dimensions. A `maxLength` written for a layout reason is a card measurement in disguise, and it rejects a user's content for something the model is not entitled to know.
- **A source says what its document says, and one transformer makes it fit a card.** `cardWithFittedStats` in `@ttrpg-cards/card` is the only place that decides how a stat block reads: it sets a value too long for its cell shorter, and lifts prose out of a trailing bracket into a block at the end of the body. Every producer builds a card in its own source's wording and hands it through, so the bundled catalog and a document a reader brought get the same answer and neither carries a copy of the rules. A mapper that normalises wording before a card exists has put the rule where only one source can reach it; run it on the card instead, once the content is canonical. It gives the same card back when there is nothing to change, so it is safe to apply wherever a card is built.
- **Printed on one side, a sheet lays out cards, not entries, and is only left short when the cards run out.** An entry that became two cards is two cards on the page: a row or a sheet with one slot left takes the first of them and the second goes on to the next. Packed as whole entries instead, a two card entry needs both slots at once, and whatever cannot give it them leaves a hole with the entry below it, which is paper spent to keep two cards adjacent on a sheet that gets cut apart before anybody reads it. Zero gaps is the rule and it is asserted directly in `SheetLayout.test.ts`, over several measurement shapes, rather than read off one arrangement. Printed on both sides it does not govern: a back page holds a gap wherever the card on the front of that slot had no continuation, which is the point of the two sided bullets under Page Geometry and Printing.
- **One rule sets a table, whoever wrote it.** `tableBlocks` in `@ttrpg-cards/card` is the only place that decides how a table reads on a card: a line naming it, then one list item per row. The card model has no table on purpose, because a grid sized for a page column does not survive being set at card width. A source's job ends at reading its own markup into runs, exactly as it does for the stat block, so a table a reader wrote comes out arranged like one from the bundled catalog.
- **Geometry reaches CSS as custom properties set inline from the layout**, never as a value in a stylesheet. The component sets `--card-width`, `--card-height`, the four margins and `--card-font-size` from the layout it is handed; the stylesheet reads those and works in ratios of them. A rule that wants a measurement has to ask for a property that exists, which is what keeps a card size out of the CSS.
- **The card's type scale and spacing are ratios, not lengths.** `--card-scale-*` say how much larger a title is than the body; the renderer works out what that is in millimetres against the live font size. A length there would be pinned to one card size. They are declared on `.card` itself, in `CardFace.module.css`, because the card face is the only thing that reads them.
- **A ratio below 1 is clamped to the layout's minimum font size.** Legibility is a length, not a ratio: a ratio follows the body text down and would scale a label past the point it can be read. The floor lives with the geometry, and the renderer resolves the whole scale once so every region gets the clamp.
- **The card gives up type size, never its box.** Fitting measures the rendered card and scales the text; the card's dimensions are what it is cut to and do not move. Content that will not fit at the bottom of the range is a second card, never a smaller card and never a cut word.
- **An entry is a set, and a set is usually one card.** `CardSet` in `@ttrpg-cards/card` owns where a split falls; `useCardSet` in `@ttrpg-cards/ui` is what a consumer asks when the content might not fit, and `CardSetView` draws the answer for a caller that wants the set read as a set rather than placed card by card. The first card is the whole card, and every card after it carries the name, the badge and the rest of the body and repeats no other region. The badge is the exception because it is what the card is rather than a repeat of something the first card said: somebody holding only the second half still has to be able to read its rank off it, and a glyph in the corner costs no height. A card of a set shows its position (`1/2`); a card that stands alone shows nothing.
- **Split first, size second, and the two never talk.** The split is settled at the floor, and then every card of the set takes the largest size its own assigned content allows, the first one included. A cut lands at a block boundary, so the first card stops short by up to most of a block, and that leftover is room type may grow into. Nothing in the sizing pass may move content between cards: that is what keeps the split reproducible, and what stops a card growing into room it then loses again. Some gap survives where the next size up would overflow, and that remainder is expected.
- **The chrome is sized by the preset and the body is fitted.** `--card-font-size-chrome` is the text size the reader picked; `--card-font-size` is what the body settled at. The band, the property labels, the footer and the spaces between regions read the first, so two cards of one entry carry identical chrome however differently their bodies are set.
- **Two pieces of chrome move, and both only for their own width.** The title steps down to fit the band and takes a second line only at the floor, and the strip's labels step down together until the longest word in each sits on one line in its cell. Neither follows the body: what they answer to is how wide their own words run in the face they are set in, which is why the step is measured rather than declared. A card of a set carries no strip, so an entry's cards still read as a pair.
- **A property label has a floor of its own, below the one the rest of the card keeps.** The general floor is the smallest size prose reads at. A label is one word in bold capitals, read as a heading for the value under it, and it holds below that: `COMPONENTS` is wider than a quarter of a card at the general floor in every face the app ships, at every text size, so holding labels to it means breaking the word in half. `--card-scale-label-floor` is how much lower they may go.
- **The inset is a function of the preset and nothing else.** A size preset declares the blank a card wants at the middle text setting, and `CARD_TEXT_SIZE_MARGIN_SCALES` brings it in or lets it out with the text size, so asking for smaller type buys the room its margins were holding. It is frozen the moment the preset is chosen: padding that moved with the fitted size would feed back into the measurement and make it chase itself.
- **The card carries one fill, and it is the position pill.** Regions are separated by rules, never by a panel behind them. A fill heavy enough to carry a boundary on its own drinks ink and grays out flat on the mono laser printer most of these come off.
- **A typeface pairing is named in `@ttrpg-cards/card` and drawn in `@ttrpg-cards/ui`**, the same shape as a theme, with one difference that matters: choosing a colour cannot move anything, and choosing a face changes how wide the text runs, so it changes where an entry splits. A pairing travels with the layout into every measurement rather than being set once on a surface above the cards. The faces are vendored beside their licences and reached by relative URL, because a webfont request is the reader's browser calling somebody else's server.
- **A vendored face belongs to `@ttrpg-cards/ui`, not to the card face.** The families and their `@font-face` declarations live in `packages/ui/src/fonts`, which is where the no-fetch rule is held; a pairing in `CardFace.typefaces.css` names families and never declares one. The card face is the first consumer of a face, not its owner, and a font in a component's directory is a font nothing else can reach without reaching into it.
- **The paper is white, and so is every card on it, whatever the desktop is set to.** The app's own surface may follow `prefers-color-scheme`; the sheet and the cards may not. A dark sheet is a lie about what comes out of the printer, and a dark card on a white sheet reads as a fault. Paper roles (`--color-paper` and its edge and ink) sit outside the dark override in `theme.css` for that reason, and a test holds every card palette to being the same on a dark screen, a light screen and paper.
- **A cut lands at a block boundary, then a sentence end, then a word end, and never inside a word.** Whitespace at a cut stays with the opening half, so the halves laid end to end are the text that came in. A block with no usable boundary left goes on whole and overflows, which is at least visible.
- **Measuring is the caller's job, not the routine's.** `CardLayout.fittedFontSize` and `CardSet.split` both take one predicate and know nothing about how tall anything is, which is what keeps them pure, testable and independent of the browser. A predicate answers by rendering the real thing and reading back where its content lands, never by estimating from character counts.
- **Every colour a card sets text on meets WCAG AA**, and a test in `@ttrpg-cards/ui` holds every theme to it by reading the stylesheet. Contrast is computed from relative luminance, so passing it is also the grayscale check.
- **Cards are made to be printed, usually on a mono laser printer, so a theme may never separate one region from another by hue.** Every boundary meets WCAG's 3:1 for non-text, either across the two fills or along the rule drawn between them, and the same test enforces it. Prefer the rule: a fill heavy enough to carry a boundary on its own drinks ink and grays out flat, which is why the tinted region is held to a tint rather than a fill.
- **A measurement is skipped when only the scale it is drawn at changed.** The screen size control draws the sheet at the reader's scale, and a `ResizeObserver` reports that as a resize even though the card and everything in it are drawn at one scale together: the box moves by a hundredth of a pixel, which is the rounding of a scaled edge. Compare `offsetWidth` and `offsetHeight`, which are the laid out box in whole pixels and do not move under a scale, and re-measure only when they do. Believing the observer costs every card on the page a fitting search per nudge of the slider.
- **A fit made in a face the card is about to stop being drawn in is not worth making.** Every face swaps in after the page has drawn, so a card that has never been measured is fitted twice, once in the fallback and once in what lands after it. A card that already carries a size measured for the same content and geometry is not: when the reader changes the pairing, the old size stands until the new faces are there, and the card is fitted once.
- **Wait for a face by name, never on `document.fonts.ready`.** That promise is for the loading already under way. A pairing the reader has just picked has not been asked for at the moment the measurement runs, so the promise is long resolved, fires at once, and the second measurement lands in the fallback as well, with nothing left to correct it. `document.fonts.load` with the element's own computed font is the question that has the pairing in it, and `check` with the same font is how you skip the wait when the face is already there.
- **A display face carries its own optical centring, in `--card-name-centre`.** Centring a line box puts the middle of the ascent and descent in the middle of the band, and what a reader sees centred is the middle of the capitals, so a lopsided face reads high or low wherever its box is put. The correction is measured in the browser with the correction off, from the band's edges to the cap line and to the baseline, and applied as a transform so the band's height and every measurement against it stay where they were. It belongs to the file: a face revendored at another weight is re-measured, and the rest are left alone.
- **A dark-scheme override is scoped to `screen`, always.** A media query with no media type means `all`, which includes print, and `prefers-color-scheme` still reports the desktop's setting while a page is printing. Unscoped, a dark palette prints as near-white text on white paper or as a sheet of solid ink. The card's fills are held to a luminance floor on paper for the same reason: contrast is symmetric and scores a black card with white text exactly as well as the white card we meant.
- Structure work so additional card sizes can be added without touching the renderer.

### Page Geometry and Printing

- **A paper measurement is written down once, in `@ttrpg-cards/printer`**, the way a card measurement is written down once in `@ttrpg-cards/card`. `PAGE_SIZE_PRESETS` and `PAGE_MARGIN_PRESETS` are those places. A feature or an app that restates 210 and 297 has made a second copy that will drift.
- **The sheet is `SheetLayout`, an immutable value object** built out of names from closed sets: a paper, a way round, a margin. Every field is a name rather than a measurement a caller made up, with one exception, so that exception is the only thing a sheet validates; the test that holds every combination the records allow to a usable content area is what keeps the rest true.
- **The exception is the paper a reader measures, and it is validated once, in the constructor.** `custom` is a first class paper alongside the published ones: `PAGE_SIZE_PRESETS` holds what was published, `CUSTOM_PAGE_SIZE` names the one that was not, and `PAGE_SIZE_NAMES` is the set a picker offers. `SheetLayout` resolves the named paper to measurements once and every getter reads that, so **no layout code learns that a sheet can be custom**: the grid, the mirror and the pagination are the same arithmetic on a paper nobody published. A measurement that arrives from a field is held to `CUSTOM_PAGE_SIDE_RANGE` and brought onto its step with `snapToRange`, because it reaches a `@page` rule as text and a paper of nine metres or of `NaN` must never get that far. `PaperName` is the narrower type for anything that has to resolve to a size on its own, a default included.
- **A custom paper's margin is `PRINTER_SAFE_MARGIN_MILLIMETRES`, and that is a floor rather than an answer.** A published paper carries the margin its own grid arithmetic came to. A paper nobody worked a grid out for has no such number behind it, so all that can be known about it is the printer: a laser's unprintable band is typically 4.2mm, a sixth of an inch, and five clears it. Whatever the grid leaves over is centred by the insets as usual. Every published paper's margin is held to the same floor by a test, because the outermost column of cards is the one that goes missing when it is not.
- **A sheet holds cards, not entries.** `capacityFor` counts card slots, and an entry that runs onto a continuation takes two of them. Anything filling a sheet has to measure before it knows how many entries go on it, so it fills optimistically, lets each entry report what it cost, and gives back what no longer fits. Count an unmeasured entry as the one card it is at least: a guess that never lowers a count is what makes that settle instead of oscillate.
- **What an entry cost is kept across a change of face or size, and only a measurement replaces it.** The last count is a far better guess at the next one than the single card a fresh mount assumes, and every entry on the page re-measures itself and says what it really came to. Thrown away instead, the page lays every entry out as one card and then moves each one that grew to the sheet after it, and every move is a remount and another round of measuring for the entry and for everything behind it.
- **Whatever the preview is drawn at, `@page` is set to.** The browser otherwise picks the paper itself and the layout re-wraps against whatever is left, so a grid that is three across on screen prints as two. Build the rule from the same `SheetLayout` the custom properties come from, so the two cannot disagree. It has to be literal text, because `@page` descriptors do not resolve `var()`. A number a reader typed may reach it, and only because `SheetLayout` has already held that number to a range and a step: the rule is asserted to be nothing but digits and units, and the harness checks a browser really printed on them.
- **`@page` carries the paper and no margin, and the sheet keeps its own blank as padding.** Nothing in the page box can be drawn in a `@page` margin, and the cut guides at the outside of the grid reach into exactly that blank, so a margin there would take them off the paper. It also makes the printed geometry the preview's rather than nearly the preview's, which is one fewer thing to keep in step. The one divergence left is the bottom padding, dropped on paper: nothing is laid out below the last row, so it buys no blank the grid was not already leaving, and a box coming to exactly the page height breaks onto a second page on a sub-pixel rounding.
- **Cut guides are marks in the blank around a card rather than an outline on it.** Eight of them, two running out from each corner, reaching out by exactly `CARD_GAP_MILLIMETRES` so two neighbours' marks meet and the cut line runs unbroken across the gutter. A drawn outline is on the card once it is cut out and any part of it the blade misses shows; a mark in the offcut is thrown away whether or not the cut was exact. They go on pseudo-elements, because a guide drawn as an element of its own would be another item in the grid and would cost the sheet a column, and they set `print-color-adjust: exact` like anything else whose colour has to survive. A blank slot carries them too: it is behind a card on the other side of the paper, so it is cut like any other.
- **Whether a sheet carries them is the reader's, and the setting reaches the page as a measurement rather than a flag.** `SheetLayout.cutGuideReachMillimetres` is the gap when they are on and zero when they are off, and `--page-guide-reach` carries that to the stylesheet. A mark of no length paints nothing, so there is one set of rules, no second stylesheet, and nothing in the page branches on the setting. The same shape as `--page-grid-row-inset`, which is zero on a sheet printed one side. Reach for it whenever a print setting turns something off: a measurement that can be nothing is cheaper than a mode.
- **A paper measurement appears in three files and nowhere else**, and `pnpm verify:print` greps the workspace to prove it: the record that declares it (`sheet.constants.ts`), the test that pins the record, and the harness that restates it to check a browser printed on it. The grep ignores comments, because an `@example` saying what a call returns is documentation of the record rather than a second copy laying anything out. There is no type that can stop somebody typing 210 into a stylesheet, which is why this is a grep.
- **The page margin belongs to the paper, not to the reader.** It is not a preference, it is whatever the grid does not need, and two papers of different sizes have different amounts spare. Letter is 17.6mm shorter than A4, so giving both the same margin costs one of them a row. Each paper carries its own `marginMillimetres` in `PAGE_SIZE_PRESETS`, and the arithmetic behind the number goes in the comment beside it so nobody later "tidies" it into a sheet of six.
- **The gap between cards and the margin are the same budget.** Every millimetre between cards comes off the margin, because both are competing for what the grid leaves. Change one and check the other.
- **A printed sheet is the cards and nothing else.** Chrome comes off, and so does the credit: the licence obligation attaches to where the material is shared, which is the app, and the notice is in full on screen. A sheet that needs to stand on its own wants a short per-sheet credit with the cut guides, not the full block.
- **A surface that stands in for paper paints itself `--color-paper` in print.** Going transparent lets the app's own background through and the sheet comes out tinted. Paper is the one colour in the theme that is a physical fact rather than a choice, so it does not follow the colour scheme.
- **Anything whose colour has to survive printing sets `print-color-adjust: exact`.** A browser drops background colours when printing unless the reader finds the background graphics option, which is off by default, so a card's theme silently prints as white paper with black text without it. Same class of fact as the `@page` rule: what the browser does to your output unless you tell it not to.
- **A surface laid out in millimetres spends no layout pixels on decoration.** Its width is the paper and its padding is the margin, so every pixel a border takes comes out of the grid: a 1px border each side is enough to push a 193mm grid out of 194mm of content and drop a whole column. Draw the decoration with `outline` or a shadow, which take no room.
- **Centre a grid by insetting it, never by centring its rows.** A wrapping flex container centres each line on its own, so a short last row stops lining up with the columns above it, and the output is a sheet somebody is going to cut along those columns. Put the inset on one side only and leave the other at the plain margin: the grid still comes out centred, and the row keeps that inset as slack, which it needs because a row asked to be exactly as wide as its cards drops its last column on a sub-pixel rounding.
- **A CSS millimetre is not a millimetre, and nothing in the browser can tell you what one is.** An inch is fixed at 96 pixels, so a length in `mm` is only physical on a 96 ppi display, and `devicePixelRatio` reports device pixels per CSS pixel rather than density. The only way to know is to ask the reader to match something they are holding against something drawn, which is what the screen calibration is for: the cards on the page are the reference, because they are the thing being got right and every size is drawn at the same scale. Apply the answer to the preview scoped to `@media screen`, and leave every measurement alone: the correction is how a sheet is drawn, never what it is.
- **The preview is scaled with a transform, and the room it takes is reserved with margins.** A `zoom` is a change of the lengths everything on the sheet is laid out in, so the browser lays every card on it out again for each step of the control, which is a fifth of a second of locked page per step on a set worth printing. A transform draws what is already laid out, which is what the reader asked for when they moved a control that cannot change the arrangement. It reserves nothing on its own, so the sheet carries the difference as `margin-right` and `margin-bottom` and the sheets below it and the credit under them land where the drawing ends rather than where the box does.
- **A measurement made through `getBoundingClientRect` is in drawn pixels, and a computed length is not.** A `zoom` or a `transform` above an element scales one and not the other, so anything comparing the two has to divide the scale back out. `offsetHeight` stays in laid out pixels under both, which makes it the denominator that tells you what the scale is.
- **A surface that can show nothing says so.** A sheet with no room for the first entry is a dead end: nothing renders, so nothing measures, so the answer never changes on its own. Name what the reader can change, because they are the only one who can change it. A blank surface is not a state, it is a missing one.
- **A sheet paginates into pages, not into sheets.** `SheetLayout.paginate` hands back a `SheetPage` per printed page: which piece of paper it is on, which side of it, and a slot index for every run of cards. Printed on one side that is one page per sheet with the slots filling from zero, which is the same arrangement it always was. Printed on both it is front and back pairs, and the slot index is the point: a back page's cards are not in reading order.
- **A continuation goes on the back of its own slot, and the rule generalises.** Odd numbered cards take a front, even numbered ones the back of the slot the card before them is on, so a two card entry is one slot and a three card entry is two with the second back blank. Do not special case the two card entry: every set of cards is the same arithmetic.
- **The mirror is derived from the flip edge and the way round the paper is, never hard-coded.** A sheet turns about the axis its flip edge runs along, so a long edge flip reverses the columns on portrait paper and the rows on landscape. `SheetLayout.mirrorAxis` reads that off the paper's own dimensions, which is what keeps it right when a reader turns the sheet. It is its own inverse, and a test holds it to that over every paper, orientation and edge.
- **Anything that spaces the preview out is scoped to `screen` or taken back off in `print`.** A rule with no media type is `all`, so the gap a reader wants between two sheets on screen is also a margin on paper, where there is nothing between two pieces of paper to space out. Whether such a margin survives a forced break is the engine's call, and one that keeps it starts a page's grid lower than the page before it, which on a two sided job is a back that no longer registers with its front. The print block already drops the width, the padding and every decoration for the same reason; spacing belongs in that list.
- **A mirrored slot is only in the right place if the grid is centred on the axis being reversed.** `mirrorSlot` answers in grid indices, and an index becomes millimetres against wherever the grid starts, so a grid whose leftover trails under the last row prints every back offset from its front by that whole leftover. `gridRowInsetMillimetres` is the row half of `gridInsetMillimetres` and it is what closes that: the page inset comes off the top, and the two insets together centre the grid both ways. Emit the row inset only for a two sided job, because it moves the grid and a one sided sheet has no back to register. Both insets are geometry on the sheet rather than modes, and both are held to being half of what their own axis leaves.
- **A blank back is still a page, and it is still printed.** A page a driver skips moves every back after it onto the wrong front, which spoils the run rather than one card. `paginate` emits it, the page renders it, and the app tells the reader to turn their driver's skip-blank-pages setting off, because none of those three can be dropped on its own.
- **Entries needing more than one card are laid out first when the job is two sided.** That gathers every blank back at the tail of the run, so a driver still set to skip blank pages drops only trailing pages and the run still comes out correct rather than every back past the first blank landing on the wrong front. It saves no paper: the page count is the sum of the slots whatever order they go in. The order on the page changes; the order the reader put the entries in does not.
- **A page that places cards at stated slots draws the gaps between them.** The sheet lays its cards out in reading order and wraps at the margin, so a card lands at the slot it was given only if every slot before it is occupied. `pageCells` turns a page's slots into cards and blanks, and the blank is a card's worth of nothing rather than no element at all.
- **What a browser does with a sheet is proved in a browser.** `pnpm verify:print` builds the export, serves it over loopback, drives the page in headless Chromium and measures what was drawn. Three phases: **every paper, printed on one side**, that a card comes out 63 by 88mm within half a millimetre, that a sheet holds the cards it has room for, that the run comes to the pages it should, that every card carries cut guides reaching outward, and that the printed file came out on the paper that was asked for; then **the cut guides turned off**, that nothing is painted around a card, which needs a browser because they come off by their reach going to nothing rather than by a rule being dropped, so the pseudo-elements are still there with their gradients in them; then **both flip edges, printed on both sides**, that the pages come in front and back pairs, that a continuation stands as far in from the mirrored paper edge as its front card does from the opposite one, and that a blank back is printed rather than dropped. A setting that has to be driven and settled again is its own phase rather than a check inside another, because running it per paper buys several answers to one question. Vitest runs in Node and in jsdom and neither has a layout engine, so a number of millimetres becomes a place on paper here and nowhere else.
- **The papers the harness drives are A4, Letter, and one typed in by hand.** The third is what says no part of the layout assumes a sheet: a paper nobody published is the one a hardcoded size breaks on, and it is the only way to drive the range check and the `@page` text end to end. Pick sizes that come to different counts, or the run proves the three papers agree rather than that any of them is right.
- **Every expectation the harness holds is restated in it, never imported from `src/`.** The mirror axis, each paper's measurements, the card's, and how many cards a sheet holds are all written out in `scripts/print.constants.ts`, with the arithmetic behind each count in the comment beside it. An expectation taken from the code under test agrees with it however wrong both are. The harness drives the app through its labels and roles rather than its internals for the same reason. Two similar-looking declarations in one package is an invitation to deduplicate them: do not, or the check quietly stops checking.
- **Every run keeps a picture of each page and a grayscale render of the first.** The renders are evidence for what a measurement cannot say, and the grayscale one is there because most of these sheets come off a printer with one toner cartridge: the contrast tests prove that from the numbers, and this is the same claim as something somebody can look at. The filter goes on for the capture and comes straight off, because it makes the element it is on a containing block and the page is measured again after.
- **Every layout input the fixture's counts rest on is picked, never left at its default.** Paper, orientation, card size, typeface, text band, sides and flip edge all decide either how many slots a sheet holds or whether the long entry splits, so a default that moves quietly changes what the measurements mean rather than failing. The colour theme is the one control left alone, because a theme is a set of colours and cannot change how much a card holds.
- **An immutable value object a reader edits is held as state directly, never unpacked into a field per setting.** The sheet is `useState<SheetLayout>` and every control hands a `SheetLayoutOverrides` back through one `changeSheet`, because `with` is already exactly that and already normalises what it is given. Held as six pieces of state instead, the same list has to be written out in the state, in the memo that rebuilds the object, in the selection type, in the props of whatever shows it, and in a callback per setting, and the one that gets missed when a seventh is added is the bug. It also means the value object is the only place a reader's input is checked, and a control shows what it settled on by reading the object back.
- **A surface that is still arriving says so with `aria-busy`, and that is what a harness waits on.** The page already works out when every sheet is up and every measurement has landed, which is what holds the print control back; publishing it is both the accessible answer and the one thing a browser outside the app can wait for. The harness still requires nothing drawn to have moved for several samples on top of it: the flag can read settled in the moment after a control changes and before the work it started reaches the DOM, and matching samples can be a scheduling gap on a loaded machine. Every sheet publishes it, the one with room for nothing included, and the harness stops the run when any of them does not: a missing attribute reads as not busy, which would leave it waiting on half an answer while still reporting a pass. A jsdom test pins the attribute both ways, because `jsx-a11y` is not enforced here and nothing else would go red for its loss.
- **Which edge the printer flips on is the reader's to state.** A browser cannot find it out, cannot set it, and drivers disagree about what they call the two. Offer both, default to the long edge, and say the chosen one back as the setting to match in the print dialog: a mismatch gives a stack of cards whose backs belong to their neighbors, and that is cheaper to prevent than to explain.

### Closed Sets a Reader Picks From

- **A measurement is `Dimensions` from `@ttrpg-cards/core`, and a CSS length comes from its `millimetres`.** A card is cut to a size and a paper is published at one, so a sheet comparing the two should need no translation between them. Writing `` `${value}mm` `` inline is the same helper for the third time.
- **A module in `@ttrpg-cards/core` is named for exactly what it holds, and holds nothing else.** `core` is the package where accretion happens, and a module that has started taking things its name does not cover is how it starts: a bounded range and a clamp under a name like `millimetres` is two concepts in a drawer labelled for one. Split it the moment you notice, which is far cheaper than after a third consumer has imported from the wrong name.
- **The contract a value is validated against cannot live in the feature that produces it.** `packages/*` may never import `features/*`, so a range or a schema kept beside its control is one no package can ever check a stored value against. That is the reason a constant with a single consumer today can still belong in a package.
- **A value a reader picks from a closed set is a `NamedOption` from `@ttrpg-cards/core`**: an `id` the code and a stored preference use, and a `name` a picker shows. Card sizes, papers, margins and orientations are all this, which is why the shape belongs to neither the card package nor the print one.
- **The name record is the single source of both the set and its order**, and `optionsFrom` turns it into the list a picker offers. Never hand-write that list beside the record: two copies of an ordered set drift, and the `Object.keys` narrowing belongs in one place rather than once per set.
- **Hold the name record to its own closed set with `satisfies`.** That is what makes the narrowing sound and what stops a value being added without a name.
- **`clampToRange` holds a value in bounds; `snapToRange` also brings it onto the step.** They are separate because most callers want only the first: a dragged control already moves in steps, and rounding a value that is merely being held in bounds would move it for no reason. Reach for the second where a reader types a measurement, which is the one case where the number arrives at whatever precision they felt like and then goes into text a browser reads. It answers at the precision the range is written at, read off how the range's own numbers are spelled rather than computed, because a step of 0.25 needs two places and its logarithm says one. **The range wins over the step**: a span that is not a whole number of steps has none sitting on its maximum, so the answer comes back on the end rather than rounded past it. What reads a snapped value is deciding whether something fits, and a value it was told is in range had better be.

### Storage

- **IndexedDB for card data. Local preferences only for small UI state** (selected theme, chosen card size, last view). Preference storage caps at a few megabytes, is synchronous, and stores strings only; the catalog alone is far too large for it.
- **No feature or app code touches a storage API directly.** Everything goes through `@ttrpg-cards/storage`. ESLint `no-restricted-globals` and `no-restricted-properties` rules enforce this, so `window.localStorage` and `globalThis.indexedDB` are blocked alongside the bare globals.
- Handle quota exhaustion explicitly: a large import can hit it. Offer a real "clear stored data" control.

### Class-Based Data Encapsulation

When a single conceptual entity has many associated computations or derivations that would otherwise be passed as raw fields to a sprawl of helper functions, **wrap it in a class** with the data on the constructor and the derivations as getters / methods (e.g. a `CardSet` or `SheetLayout` value object).

- **Trigger**: more than ~5 free functions all read the same shape of input, or call sites repeatedly destructure the same fields and pass them around.
- **Don't trigger** for one-off helpers, pure transforms, or anything without persistent context.
- Place the class in its owning package with a co-located `<entity>.test.ts`. Public API gets TSDoc.
- **Constructor takes a single options object** so the call site reads as `new SheetLayout({ dimensions, margins })`, not positional args.
- **Use `private` or `#` on a declared field for internal state**, never the underscore-prefixed convention, and never a constructor parameter property (`constructor(private readonly x: T)`), which `erasableSyntaxOnly` rejects. Declare the field, then assign it in the constructor body.
- Expose getters for derived values (`get overflows()`) and methods only for actions or parameterised reads; statics for construction helpers.

### UI Package (Radix)

- **Use `@ttrpg-cards/ui` whenever a primitive exists** (Button, Card, Dialog, Select, Tabs, Toast, Input, …). Feature components compose these. Never reimplement a primitive in `apps/web` or a feature if the UI package already ships one.
- **Add new primitives to `packages/ui/src/<PrimitiveName>/`, not to `apps/web`.** A "primitive" is anything feature-agnostic; if two features would share the same building block, lift it into the UI package with a story and tests. **Add it to `src/index.ts` at the same time**: the barrel is the package's public surface, so a primitive missing from it is reachable only by subpath and invisible to anything reading the entry point. Call sites still import the subpath.
- **A control that offers a closed set of values takes them and hands one back in the consumer's own type.** `ChoiceGroup` narrows what was picked against the options it was given, so a caller holding a union needs no assertion. A primitive that reports a bare `string` pushes a cast onto every consumer.
- **A primitive reports the action, not the event.** `Button` takes `onPress: () => void` and `ChoiceGroup` takes `onValueChange`, so no consumer ever learns what kind of event reached the control and the control can change what it listens for without changing anyone.
- **A control a reader types a number into reports when they have finished, never per keystroke.** `NumberField` holds what is being typed and tells the caller on blur or Enter, then goes straight back to showing `value`. Half a number is not a number: a caller holding the answer to a range would take the 1 off a reader on their way to 148 and they could never get there. Reporting late is also what makes the correction visible, since what the field shows afterwards is whatever the caller settled on rather than what was asked for. The caller owns the range, because the caller owns what the number means. A quantity with no number worth stating wants a `Slider` instead.
- **Such a field blurs on the wheel rather than stepping.** A browser steps a focused number input on the wheel, and reporting late is what makes that dangerous: a reader who types a measurement and then scrolls to look at what it did moves it without seeing it move. Blur rather than cancel the event, because React listens for the wheel passively and a `preventDefault` there does nothing. Scrolling away is leaving the field anyway, so the blur commits what was typed.
- **A component that measures takes an escape hatch for a caller that already measured.** `CardFace` takes `fontSizeMillimetres` and `CardSetView` takes `set`; given one, neither measures. This is not an optimisation to add speculatively, it is what stops a caller that needs the answer for its own layout from paying for the same measurement twice.
- **Never render a bare `div`, `p` or `span`.** Use `Box` from `@ttrpg-cards/ui/Box`: a `div` by default, `as="p"` or `as="span"` for the other two. The generic containers then come from one place, so a change to what a container is happens once. An element that carries meaning of its own, a heading, a list, a list item, an article, stays itself rather than hiding behind a generic name, which is why `Box` takes those three and no more.
- **Controls that stand in a row share one height, `--control-height` in `theme.css`.** A segmented track, a slider and a button are made of different parts and, left alone, land within a pixel or two of each other, which reads as crooked rather than as varied. A control added later joins the row by honouring the same property, not by being nudged at a call site.
- **A tooltip is help, never the only place something is said.** It answers a pointer and a keyboard focus and nothing else, so a reader on a touch screen may never open one. Put what a reader must know to use the control at all in its label; put in the tooltip what they would only wonder. A control that cannot be used without reading its tooltip wants a better label.
- **A tooltip trigger is the child itself, and the child has to take a ref.** Radix clones it, so nothing in this package can be one: none of the primitives here forwards a ref, and a wrapper element would put a box in a layout that was not asking for one.
- Layout knobs go on the primitive's props, not on consumer CSS.
- **Run Storybook (`pnpm storybook`) when adding or modifying a primitive** so the new variant is visually verifiable, and add a `.stories.tsx` alongside it.

### Code Style

- **TypeScript only. There is no JavaScript in this repo, and `allowJs` stays off.** Next's generated `tsconfig.json` sets it; it has been removed deliberately and must not come back. A `.js` or `.jsx` source file is a mistake, not a shortcut. Config files that must be JS (`eslint.config.mjs`) are linted like everything else.
- **Compiler strictness is a floor, not a preference.** `tsconfig.base.json` turns on `strict` plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitReturns`, `noImplicitOverride`, `noUnused*`, `noFallthroughCasesInSwitch`, `erasableSyntaxOnly`, and disallows unreachable code and unused labels. Do not relax one to make a change compile; fix the code. (`noPropertyAccessFromIndexSignature` is the one deliberate omission: CSS Modules are typed as an index signature, so it would force `styles["card"]` at every call site and fight the styling convention.)
- **`erasableSyntaxOnly` is on: enums, parameter properties, and namespaces are not available.** Packages ship TypeScript source that is type-stripped rather than compiled, so a construct that needs a runtime transform cannot survive the pipeline. The error is `TS1294`, and the answer is never to switch the flag off:
  - Instead of an enum, use a `const` object with a derived union: `const PAPER_ORIENTATIONS = { portrait: "portrait", landscape: "landscape" } as const; type PaperOrientation = keyof typeof PAPER_ORIENTATIONS`. It stays a plain object at runtime and new entries are additive. Use it only where the set really is closed; card dimensions are not, so see Card Geometry before reaching for it there.
  - Instead of `constructor(private readonly x: T)`, declare the field and assign it in the constructor body.
  - Instead of a namespace, use a module.
- **Never use nested ternaries.** Extract a function with clear `if`/`return` paths. A single ternary is fine; nesting one inside another is not.
- **Never spread a conditional expression.** That covers a ternary, `push(...(cond ? a() : b()))`, and a nullish fallback, `[...(maybe ?? []), next]`. Both hide a decision inside an expression that reads as plumbing, so the reader has to work out what is being chosen and what is being unpacked at the same time. Write the branch out with `if`/`else`, or name the value first and use that. This is the same objection as the conditional object spread below: build the thing, then use it. Reaching for the fallback form is usually a sign the value wants a named helper anyway, and the accumulate-into-a-map case (`map.set(key, [...(map.get(key) ?? []), item])`) is also rebuilding the array on every item, so writing it out is faster as well as clearer.
- **Add TSDoc comments** to exported functions and non-trivial helpers. Don't overdo it, and skip comments for obvious one-liners.
- **Give exported API a TSDoc `@example`.** A signature says what the arguments are; an example says what comes back, and it is what shows on hover at the call site. Use a fenced ```ts block, keep it to the shortest call that is still real, and put the result in a trailing comment. Show the failure case too when there is one worth knowing (`RichText.of(""); // throws TypeError`). Favour examples generally, not only on the public surface: anywhere the shape of the return value is not obvious from the type, one is worth more than a sentence.
- **Keep comments concise.** A comment states, briefly, _what_ the code does and _why_ it exists, nothing else. Don't explain how a framework works, don't narrate history ("used to X, now Y"), and describe only the current state. Reserve verbosity for a special-case branch, a non-obvious invariant, or a gotcha a future reader must know.
- **Use full variable names.** Never abbreviate (`sourceEntry` not `srcEntry`, `cardIdentifier` not `cardId` where ambiguous).
- **No underscore-prefixed private fields.** Use `private` or `#` on a declared class field, assigned in the constructor body, not a parameter property.
- **Use object params for ambiguous signatures.** Two or more parameters of the same type, or any boolean parameter, get wrapped in a single options object so call sites are self-documenting.
- **No chained `??` for multi-step selection.** Assign each fallback candidate to a named `const` and return it with an early `if (x) return x;` guard.
- **No conditional object spread for optional fields.** Never build a literal with `...(cond ? { key: value } : {})`. Set the field inline (`key: cond ? value : undefined`) or assign it after the literal so the object's full shape stays readable. Because `exactOptionalPropertyTypes` is on, a property you assign `undefined` to must be declared to accept it: `note?: string | undefined`, not `note?: string`. Declare it that way whenever the inline form is used; if you hit `TS2375`, that is this rule talking, and the fix is the property's type, never a conditional spread.
- **Use `clsx`** for merging class names. Never concatenate class strings manually.
- **No inline functions in JSX** (e.g. `onChange={(e) => ...}`). Define handlers in the component body or `.hooks.ts`. Don't reach for `useCallback` unless passing the function to a child that needs a stable identity.
- **Code must not acknowledge the review/task process.** Comments, identifiers, strings, and tests describe _what_ the code does and _why_, in product terms, never a reviewer, a task/issue tracker id, or "the former X we migrated from". A requirement is documented as the code's own rationale.

### Writing Style

Applies to everything written here: comments, docs, READMEs, identifiers, and user-facing copy.

- **Write in natural language**, the way a person would explain it out loud.
- **No em dashes anywhere.** Not in comments, not in docs, not in identifiers or strings. Use a comma, a colon, parentheses, or a second sentence instead.
- **Keep comments concise.** Say what the code does and why it exists, then stop. One line is usually enough. (The comment rules under **Code Style** above are the detail.)
- **Keep documentation concise.** Lead with the rule, skip the preamble, and do not restate what the reader just read.
- **No filler, hedging, or throat-clearing.** If a sentence adds no information, delete it.
- **User-facing copy is American spelling: "Color", not "Colour".** This is the same split that already puts `license` in a wire-format key while the prose around it writes "licence": what a reader sees follows their spelling, and our own prose keeps ours. Labels, buttons, empty states and error messages are user-facing; comments, docs and READMEs are not.

### Testing

- **Test framework**: Vitest. Tests live next to the file they cover, using the `.test.ts` suffix (`fitting.ts` → `fitting.test.ts`).
- **All utility functions, helpers, parsers, and pure hooks must have thorough unit tests.** Every exported function in a package's `src/**/*.ts`, and in `.data.ts` / `.hooks.ts` files, should be covered.
- Use `describe` blocks grouped by function/class with clear `it` descriptions. Mock external dependencies (storage, `fetch`, timers) with `vi.spyOn` / `vi.mock` and restore in `afterEach`.
- **Edge cases are mandatory**: zero/empty inputs, malformed input, missing data, error paths, boundary conditions, not just the happy path.
- **Sample data shared by more than one test file goes in `<module>.fixtures.ts`** beside those tests, never in a `.test.ts` that another test imports. Keep fixtures out of the package barrel: they are test input, not public API.
- Packages run in Vitest's default Node environment. `@ttrpg-cards/ui` runs in `jsdom`, configured in `packages/ui/vitest.config.ts`.

## Tooling

- **A package-specific ignore lives in that package's own `.gitignore`.** `packages/srd/.sources` belongs in `packages/srd/.gitignore` as `.sources`, not in the root file with a path prefix. The rule then travels with the package, and the root file stays about the workspace.
- **Turborepo orchestrates workspace tasks.** `pnpm lint`, `pnpm typecheck`, and `pnpm test` route through `turbo run`; single-package and long-running/mutating tasks (`dev`, `build`, `format`) stay on plain pnpm. Only those three tasks are defined in `turbo.json`; a task with no matching root script does not belong there.
- **Every file that defines a rule belongs in `globalDependencies`.** `eslint.config.mjs`, `tsconfig.base.json`, and the rest listed in `turbo.json` are in the global hash, so relaxing a boundary invalidates every cached task result. Without that, the gate replays a stale pass at the exact moment it matters most. Add new root-level config there when you introduce it.
- **Always install the latest stable version** of a new package, and record it in the `catalog` in `pnpm-workspace.yaml` rather than in the consuming manifest.
- **CI runs the same gate as `Pre-submit Checks`, on every pull request and every push to `main`** (`.github/workflows/ci.yml`), plus `build-storybook`. There is one definition of the gate: when you add a command here, add it there, and keep the order the same so a CI failure maps onto a command you can run locally.
- **Anything needing the network runs in a job of its own.** `Catalog drift` downloads the licensed documents and `Print verification` downloads a browser, so neither belongs in the gate: a clone has to typecheck, test and build with nothing but the repository. They are separate jobs rather than optional ones, and both are real signals about the change under test.
- **Pin a GitHub Action to a full commit SHA**, with the version in a trailing comment (`uses: owner/action@<40-char-sha> # v1.2.3`). A tag, even an exact one, can be re-pointed by whoever owns the action, and CI runs third-party code over a checkout of this repo. A new action is a new dependency: the latest-stable rule applies, and so does the supply-chain caution behind `minimumReleaseAge`.
- **A new version waits out `minimumReleaseAge` before it is installed**, so a compromised publish has time to be caught and pulled. Bypassing it means adding an exact `name@version` to `minimumReleaseAgeExclude` with a reason, not lowering the floor.
- Two deliberate toolchain splits exist because upstream support lags. Revisit each when the upstream packages catch up:
  - **TypeScript**: packages compile and typecheck with the current major (`catalog: typescript`). The lint toolchain resolves an older major (`catalog:lint`) because typescript-eslint refuses to load against the newer compiler API.
  - **ESLint**: the config is composed only from plugins that support the installed ESLint major. React and accessibility plugins are not yet compatible, so `react/*` and `jsx-a11y/*` rules are **not currently enforced** even though the conventions above still apply, so review for them by hand. **Pinning ESLint back to regain those rules is settled and rejected.** The import and transmission boundaries are what this config exists for and they need the current major; losing some rules is the accepted price. Restore the plugins when upstream ships support, and do not re-open the trade.

### Build Scripts and Generated Data

Tooling a person runs by hand lives in `packages/<name>/scripts/`, under the package whose subject it is: the generator that writes a package's own source data, and the harness that proves a package's output is really what a browser does with it. `apps/web` is a thin wrapper and stays one, so nothing that is not the app itself goes in it.

- **A script belongs to the package it is about, not to the thing it happens to run.** The print harness drives the built export, so it looks like it belongs beside the app, but what it checks is sheet layout, which is `@ttrpg-cards/printer`. Whoever changes the mirror arithmetic is the one who needs the harness under their nose. A script that needs a built artifact takes its path as an argument rather than working it out, because a package computing a path inside `apps/web` is the dependency direction backwards; the root script that builds the export is the one that knows where it went.

- **A build script never runs at build time, and the quality gate never depends on it.** It is a `pnpm --filter <package> <script>` a person invokes when the input changes. A CI job may run one to check the committed output still matches, but it does so in a job of its own that nothing else depends on, so a build and a clone never need the script's inputs.
- **A verification script is a job of its own, never part of `pnpm test`.** `pnpm verify:print` needs a build and a downloaded browser binary, and a clone has to keep testing offline, so it sits outside the gate exactly as the generated-data check does. It is also the test rather than a thing with tests: its helpers are proved by the run failing, so do not write Vitest tests over them. Give it a fixture that makes the run fail loudly when the thing it was checking stops happening, which is what the split entry and the blank back are in `print.fixtures.ts`.
- **`no-console` is off under `packages/*/scripts/`, and nowhere else.** Reporting what it did on stdout is a script's whole interface, and none of it is ever bundled. That carve-out is the only one: **Code Style applies to a build script in full**, including full variable names and one class per file. A script ported from elsewhere gets read by whoever has to change it next, and a PDF layout parser is the last place to keep one-letter names.
- **A package with scripts keeps a second tsconfig for them.** `types: ["node"]` and `allowImportingTsExtensions` belong to `tsconfig.scripts.json` covering `scripts/**`, and that package's `typecheck` runs both. Setting them package-wide would let a file under `src/` reach for `node:fs` and still typecheck, in packages whose whole job is to run in a browser.
- **A script's dependency is weighed like any other, and a CLI is the wrong shape for one.** Hand-run tooling is not shipped, but it is still installed, locked, audited and waited out by `minimumReleaseAge`, so "it is only a script" does not buy a package a free pass. Prefer a library to a command line tool: driving a CLI means spawning a process and scraping its output, and the tools aimed at people carry terminal colours, boxes, clipboard access and update checks that call a registry, which is a poor fit for a repository whose headline rule is that nothing transmits. Where the off-the-shelf option would replace only part of what we wrote, count the rest: half a file saved for a handful of packages is a wash, and a wash goes to the code already here. Write the reasoning next to the thing, because the next reader will ask.
- **Scripts run as TypeScript, type-stripped by Node.** That means relative imports inside a script carry the `.ts` extension, which is why those packages set `allowImportingTsExtensions` and add `scripts/**/*.ts` to their tsconfig `include`.
- **No tracked source file downloads anything, scripts included.** A licensed or pinned input goes in a gitignored directory and the script verifies its checksum before reading it, refusing anything that does not match. When CI needs that input it fetches it in a workflow step, never from TypeScript, so the transmission ban keeps its lint enforcement and needs no exemption. A hash that stops matching is a stop-and-escalate, never a pin to update.
- **Generated data stays committed, and a CI job proves it still matches its generator.** The job fetches the inputs, re-runs the script and fails on any difference, which makes the script the single source of truth without putting a third-party URL on the critical path: it is separate from the gate, so a clone still typechecks, tests and builds offline. Distinguish the failure modes: real drift or an input that no longer matches its pin fails the job, because both need a person; an unreachable upstream only warns, because an outage says nothing about the change under test. Read the pins from the manifest the script already owns rather than restating them in the workflow; the copy that goes stale is the one deciding whether the bytes are the ones we pinned.
- **Verify a downloaded input where it lands, and cache it only once something has vouched for it.** Checking at the point of download reports a truncated transfer as the fetch failure it is, instead of letting it resurface on a later run as a false alarm about the input having changed. Split `actions/cache` into `restore` and `save` so a half-finished download is never stored: a cache key that does not move until a pin changes will otherwise serve the bad bytes to every run after it.
- **Generated data files go in `.prettierignore`.** A formatter re-wrapping them puts the repository out of step with what the generator produces, and the next run shows up as a spurious diff.
- **A generated file's shape is asserted once where it is imported, and pinned by a test.** A JSON import widens every literal union to `string`, so re-checking it on every load costs real time for input our own pipeline wrote and validated. The test that holds the file to its schema is what keeps the assertion honest; say so in a comment next to the assertion.
